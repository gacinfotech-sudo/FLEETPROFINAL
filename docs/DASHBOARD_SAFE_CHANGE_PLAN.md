# Dashboard — Safe Change Plan

## Phase 1 (this patch) — safe, implemented

1. **Make the 4 `EnhancedStats` KPI cards clickable**, navigating into their already-existing corresponding views (`revenue`, `history`, `fleet`, `drivers`), with the Total Drivers card's click conditional on the current role actually being allowed into the `drivers` view (managers are not — see click matrix). Pure additive `onClick`/keyboard-activation/`role="button"` changes to one existing file; zero change to what data is fetched or how totals are computed.
2. **Centralize the "upcoming booking" business rule for full-document consumers.** `server/services/upcomingBookings.ts` already has a correct, centralized definition (`PRE_DISPATCH` status set + local-timezone day boundary) used by `buildUpcomingBookings()`. That function forces a summarized shape unsuitable for reopening the existing "Booking Details" dialog faithfully. Adding one new exported function that reuses the exact same filter/day-boundary logic but returns full booking documents (not a redesign of the existing function, which is untouched) closes this gap without inventing a second, divergent definition.
3. **Add one new read-only route**, `GET /api/dashboard/upcoming-bookings`, reusing the existing `storage.getBookingsByTenant()` call (already used by `/api/bookings` and `/api/operations/upcoming-bookings` — no new query pattern introduced) and the new service function above. Capped at 200 forward-looking bookings for the `future`/`all` buckets with a `truncated` flag, so this new endpoint doesn't introduce a new unbounded-payload risk even though the underlying DB call itself is already unbounded elsewhere (a pre-existing, separately tracked issue — [REAL_WORLD_WORKFLOW_GAPS.md](./REAL_WORLD_WORKFLOW_GAPS.md) Gap 10).
4. **Replace the existing "Upcoming Bookings" Card's content** (not its title, not its position, not its existence) with Today/Tomorrow/Future/All Upcoming tabs backed by the new endpoint, row-click opening the pre-existing `viewingBooking` dialog (`dashboard.tsx:2028`) — zero new booking-detail rendering logic, zero new booking-edit logic, 100% reuse of the existing dialog which already contains Payment recording, Extend/Reschedule, and WhatsApp communication as its own existing quick actions.
5. Add loading skeleton, per-tab empty states with a "Create Booking" action, and an isolated retry-capable error state for the new query — this section already fails independently of `EnhancedStats`/Quick Actions since it's a separate `Card` with its own `useQuery`.

**Files touched:** `client/src/components/dashboard/enhanced-stats.tsx`, `client/src/pages/dashboard.tsx`, `server/services/upcomingBookings.ts`, `server/routes.ts`. No other file.

**Files intentionally not touched:** `sidebar.tsx`, `header`, any route file beyond adding one handler, `Customer`/`Booking`/`Driver`/`Fleet`/`Vendor`/`Payment`/`Invoice`/`WhatsApp`/`GPS`/`HR`/`User Management` modules, the database schema, any existing API's request/response shape, the separate `upcoming-bookings.tsx` page or its `GET /api/operations/upcoming-bookings` endpoint (left exactly as-is), and `GET /api/bookings/upcoming` (left exactly as-is — still valid, just no longer the data source for this one card; flagged for later cleanup, not deleted now, per the brief's own "report duplication, don't auto-delete" instruction).

## Phase 2 — done

- Wired the already-existing `GET /api/operations/live-bookings` into a "Live Operations" mini-board section (Start Due/Delayed Pickup/Running Trips/Ending Soon/Completion Overdue/Payment Pending/Unassigned counts, each clickable into the existing Live Bookings screen with the matching tab).
- Fleet/Driver status board — client-side reduction over the already-fetched `/api/vehicles`/`/api/drivers` lists, each segment clickable into `fleet`/`drivers` filtered by status.
- Finance overview ("Today's Collection", cash/UPI/bank/card/other split) — new `GET /api/dashboard/finance-summary`, ledger-sourced (`PaymentTransaction`, `status: 'completed'`, today only, matching the prior audit's [SECURITY_AND_DATA_RISK_AUDIT.md](./SECURITY_AND_DATA_RISK_AUDIT.md) financial-accuracy guidance — never a raw booking-field sum), gated behind `canViewRevenue()`, whole card clickable into `revenue`.
- Lead/booking-source summary chart ("Booking Sources") — new `GET /api/dashboard/lead-sources`, a real aggregation over `Booking.bookingSource`; each bar clickable into `history` filtered to that exact source.

See [DASHBOARD_CLICK_ACTION_MATRIX.md](./DASHBOARD_CLICK_ACTION_MATRIX.md) for the full per-element breakdown and [INQUIRY_BOOKING_TEST_REPORT.md](./INQUIRY_BOOKING_TEST_REPORT.md) Phase 9 for test results (this work landed after the Inquiry/Lead/Booking mega-patch was already in progress on the same branch, so its test report absorbed the phase numbering).

## Explicitly unsafe / deferred, with the exact blocking dependency

| Requested feature | Why unsafe to build now | Minimal prerequisite |
|---|---|---|
| Company/Brand and Branch global filters (Section A) | Zero brand/branch data model exists anywhere in the schema — confirmed by grep in the prior full audit ([MULTI_BRAND_BRANCH_AUDIT.md](./MULTI_BRAND_BRANCH_AUDIT.md)). Adding a filter control with nothing behind it would be a fake/non-functional UI element, which the brief explicitly prohibits ("no decorative charts without meaning," "every card must be clickable" implying every filter must actually filter something real). | The structural `Branch`/`Brand` model + `branchId` scoping work described in that audit's "recommended solution shape" — a Large, dedicated project, not a dashboard patch. |
| CEO Vendor metrics (Vendor Duties, Vendor Payable/Receivable, Vendor Performance) | No Vendor Master/ledger exists on this branch at all ([REAL_WORLD_FEATURE_MATRIX.md](./REAL_WORLD_FEATURE_MATRIX.md) §Vendors) — this data literally does not exist to aggregate. | Merge `feature/vendor-360-patch` (already built elsewhere, per the prior audit's roadmap Phase 0). |
| GPS Online/Offline fleet metrics | No GPS module exists on this branch ([REAL_WORLD_FEATURE_MATRIX.md](./REAL_WORLD_FEATURE_MATRIX.md) §GPS). | Merge/integrate the GPS foundation from `repair/full-saas-stabilization` (roadmap Phase 3). |
| Alerts & Approvals panel (Payment/Discount/Refund/Vendor-Settlement Approval workflows) | No approval-workflow entity exists in the schema for any of these — building the panel would mean inventing a new approvals subsystem, not making an existing feature clickable. | Product decision + new data model design, out of scope for "dashboard-only + additive" mode. |
| Documents Expiring alert (vehicle/driver) | The underlying expiry-date fields don't exist yet on `Vehicle`/`Driver` ([REAL_WORLD_WORKFLOW_GAPS.md](./REAL_WORLD_WORKFLOW_GAPS.md) Gaps 3–4). | Add the expiry fields first (already-scoped Phase 2 item in the main roadmap), then this dashboard card becomes trivial to add. |
| Full profit/margin CEO metric with permission gating | `canViewRevenue()`-style permission exists and could gate a margin card, but margin requires Expenses (exists) netted against Revenue (exists) — this is actually buildable safely; deferred only because it wasn't in this patch's Phase 1 scope, not because it's unsafe. | None — candidate for Phase 2. |
| True cursor/offset pagination for "All Upcoming" | Would need a paginated list UI component and a paginated backend contract change beyond the simple 200-row cap used in Phase 1. | Scope as its own small follow-up once the 200-row cap is found to be insufficient in practice. |
