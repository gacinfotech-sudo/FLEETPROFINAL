# Pipeline Bug Report — Complete SaaS Pipeline Audit

Findings from 5 parallel evidence-based research passes (file:line cited) plus direct verification, covering pipelines A-D (Inquiry→Lead→Quotation→Customer), I-L (Driver Duty→Trip lifecycle), O/Q/P (Payment/Vendor/Feedback-Rewards), R/S (WhatsApp/Calling), routes/permissions/tenant-isolation, and DB relationships/status-transitions/idempotency. Booking/Customer/Invoice/Costing/Filters pipelines were already deeply audited in the prior "Professional Booking" initiative this session — see `docs/BOOKING_REAL_WORLD_GAP_ANALYSIS.md` for those findings; not repeated here.

Classification legend and severity per the spec's own scheme (`SECURITY_RISK`, `FINANCIAL_RISK`, `DATA_LOSS_RISK`, `PARTIALLY_WORKING`, `DISCONNECTED`, etc.; P0=critical, P1=core pipeline broken, P2=incomplete workflow, P3=usability).

## Repaired this phase

| # | Finding | Classification | Severity | Root cause | Fix | Status |
|---|---|---|---|---|---|---|
| 1 | `GET /api/reports/revenue`, `/driver-performance`, `/vehicle-performance` had `authenticateUser, requireTenant` only — **no permission check at all**. Any authenticated tenant user (including a manager whose UI hides these) could call them directly and receive full profitability/revenue data. Frontend-only enforcement (`restrictedForManagers` in sidebar/dashboard) is not a security boundary. | SECURITY_RISK / BROKEN_PERMISSION | **P0** | The `PERMISSIONS.VIEW_REVENUE` constant already existed (`server/middleware/permissions.ts`) and is used by the frontend's `usePermissions().canViewRevenue()`, but was never actually attached to these 3 backend routes. | Added `requirePermission(PERMISSIONS.VIEW_REVENUE)` to all 3 routes (`server/routes.ts:1426,5395,5414`). | **Fixed, tested** (`tests/e2e/pipeline-audit-permission-repairs.spec.ts`, 6 tests). |
| 2 | `POST /api/bookings` had **zero duplicate-request protection**. A double form-submit, browser back-then-resubmit, or a retried request after a dropped network response created two distinct Booking documents — each with its own vehicle/driver hold and its own revenue count. | DATA_LOSS_RISK / DUPLICATE_PROCESSING / FINANCIAL_RISK | **P0** | No idempotency mechanism existed on this route, unlike WhatsApp sends, reward transactions, and payment reversals, which all already use the established `idempotencyKey` + partial-unique-index pattern. | Added additive `Booking.idempotencyKey` field (optional, partial unique index on `{tenantId, idempotencyKey}` mirroring `PaymentTransaction`/`RewardTransaction`), a pre-check + a race-safe duplicate-key catch in the route, and client-side key generation (one per booking-wizard session, regenerated only on explicit "Create New Booking") in `enhanced-booking-form.tsx`. | **Fixed, tested** (`tests/e2e/pipeline-audit-idempotency-repairs.spec.ts`, test 1 and 3). |
| 3 | `POST /api/bookings/:id/payments` never accepted or forwarded an `idempotencyKey`, despite the underlying `recordPayment()` service fully supporting one (used correctly elsewhere, e.g. `reversePayment`). A double-click or retried payment-recording request created two separate `PaymentTransaction` rows, inflating `advanceReceived`. | FINANCIAL_RISK / DUPLICATE_PROCESSING | **P0** | The route destructured a fixed field list from `req.body` that simply omitted `idempotencyKey`. | Route now accepts and forwards `idempotencyKey`. Both frontend callers (`customer-dashboard.tsx`'s `recordPaymentMutation`, `payment-section.tsx`'s `addPaymentMutation`) generate a fresh key when the Record Payment dialog opens, reused for retries within that dialog session. | **Fixed, tested** (`pipeline-audit-idempotency-repairs.spec.ts`, test 2). |
| 4 | Sub-user `DELETE /api/users/sub-users/:userId` and `PATCH /api/users/sub-users/:userId/reactivate` were missing the `requireTenant` middleware present on the sibling create/list routes. Narrow edge case: an orphaned admin/client user with no `tenantId` could deactivate/reactivate *any* tenant's manager by guessing a `userId`, since `scopeTenant(req)` would pass `undefined` and the storage query would be unscoped. | TENANT_ISOLATION_RISK | P2 (narrow edge case, inline role-check already blocks non-admin/client) | Two routes simply never had the middleware other sub-user routes have. | Added `requireTenant` to both routes, matching the existing sibling routes exactly. | **Fixed** (no dedicated new test — covered incidentally by the existing sub-user tests in `availability-engine.spec.ts`'s `beforeAll`, which continued to pass). |
| 5 | Draft Invoice's "Finalize & Lock" button rendered unconditionally regardless of the viewer's permission — backend already correctly enforces `PERMISSIONS.GENERATE_INVOICE`, so this was a UX gap (a manager without the permission would click, then get a 403) rather than a real security hole. | BROKEN_PERMISSION (frontend/backend mismatch) | P2 | `customer-invoices.tsx` never imported/used the existing `usePermissions().canGenerateInvoice()` hook already used elsewhere in the app for exactly this. | Button now shows disabled with an explanatory tooltip when `!canGenerateInvoice()`, matching this same file's own established pattern for the Email/WhatsApp buttons on drafts. | **Fixed, regression-tested** (`invoice-send-gating.spec.ts` still passes with the owning-tenant client role, which has the permission). |

## No action needed (verified correct)

- Payment reversal (`reversePayment`), reward-point transactions, and Google-review-request idempotency (exact-retry case) all use the correct, DB-level-enforced idempotency pattern already.
- All four centralized status-transition validators (Booking/Lead/Inquiry/Quotation) are real, consistently enforced, and none has a raw unvalidated `.status = req.body.status` bypass.
- No wholesale `record = req.body` overwrite pattern exists anywhere in the 5 audited update routes (Vehicle/Driver/Booking/Customer/Invoice) — all go through either a Zod partial schema (which strips unknown keys) or an explicit field allowlist.
- Invoice snapshotting is correct: `customerSnapshot`/`billingSnapshot`/`businessSnapshot`/`bookingSnapshot` are plain-data copies at generation time, never live-populated, so editing a Customer later cannot silently rewrite a finalized invoice.
- Tenant isolation spot-check (5 different models) found `tenantId` is consistently server-derived from the authenticated session (`req.tenantId`), never client-supplied, in every query checked.
- `findOrCreateCustomer` is genuinely shared/reused (not duplicated) by both the Inquiry/Lead/Quotation→Customer pipeline and the direct booking-creation path.
