## What is explicitly NOT_RECOMMENDED / PROHIBITED_OR_EXCESSIVE as a document type

- Biometric scans (fingerprint/face templates) — `NOT_RECOMMENDED` by default, per
  `DRIVER-DATA-MINIMIZATION-MATRIX.md`; do not add as a selectable `documentType` without
  a separate, explicit adviser-approved feature decision.
- Any document type whose sole purpose is storing a third party's (e.g. a reference
  contact's) personal documents — out of scope; the Contact/Reference model records
  *verification status*, not the reference's own ID documents.
- Unmasked full Aadhaar number as a *searchable/displayed* field anywhere outside the
  restricted-access document view itself — `PROHIBITED_OR_EXCESSIVE`.

## Verification workflow (applies to every expiry-bearing type)

1. Upload → `uploadedBy`/`uploadTime` recorded, `verificationStatus=pending`.
2. Reviewer with the relevant permission verifies → `verifiedBy`/`verificationTime` set,
   `verificationStatus=verified` or `rejected` (with a reason).
3. On `expiryDate` approach (configurable lead time, e.g. 30 days), `TASK-DRIVER-OPERATIONS-06`'s
   expiry-alert job surfaces it — tested by `TASK-DRIVER-QA-SECURITY-07`.
4. A rejected or expired document does not retroactively invalidate historical bookings
   already completed under it — matches "protect historical... data," this only affects
   forward-looking assignment eligibility (`TASK-DRIVER-DOMAIN-02`'s assignment-eligibility
   logic reads current verification status, never rewrites past records).
