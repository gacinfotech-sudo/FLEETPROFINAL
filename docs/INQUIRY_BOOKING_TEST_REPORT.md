## Scope of Phase 11 — User-reported bug fixes + WhatsApp PDF attachments

Five real, verified issues from live user reports on this same branch, plus the remaining `WhatsAppProvider.sendDocument` follow-up already flagged in Phase 4/10.

**1. Quotations stuck at "Approved," blocking Convert to Booking forever.** "No accepted quotation" was the *correct* response — but the only path from `approved` to `sent` was "Send on WhatsApp," which only succeeds with a connected session (this tenant's isn't, like every other WhatsApp-dependent feature this whole session). No manual fallback existed. Added **"Mark as Sent (manual)"** — reuses the existing generic quotation status-transition route verbatim, no backend change.

**2. Raw JSON error toasts.** The `apiRequest()` gotcha (fixed once already in Phase 4's `quotation-panel.tsx`) recurred in 4 places in `leads.tsx` and 3 more in `quotation-panel.tsx` — an invalid status change or a rejected action showed the whole raw JSON response body instead of the human-readable reason, making correctly-working validation look broken. Fixed all 7 with the same `extractApiErrorMessage()` pattern; also added it to `dashboard.tsx` for the fix below.

**3. WhatsApp PDF attachments** — closes the gap explicitly deferred in Phase 4 and Phase 10. `WhatsAppProvider` gained `sendDocument()` (implemented in both `MockProvider` and `BaileysProvider`, using Baileys' native `{document, mimetype, fileName, caption}` message shape). PDF generation stays entirely client-side (the existing, already-tested `html2pdf` render used for "Download PDF" — no server-side PDF rendering was introduced); the client now uploads the same bytes instead of only downloading them, via a new `POST /api/quotations/:id/send-whatsapp-pdf` (multer memory storage, `application/pdf` only, 8MB cap). `sendQuotationMessage.ts` gained an optional `pdf` parameter — text-send and PDF-send are independently idempotent (distinct `messageType`/idempotency key), so sending one never blocks sending the other. **Verified live end-to-end** against a temporary `WHATSAPP_PROVIDER=mock` instance on a second port (same DB): a real 143,771-byte PDF reached the mock provider with the correct filename and Hinglish caption, and the quotation correctly flipped to `sent`. The failure path (this tenant's actual disconnected Baileys session) was also verified live: clean structured error, quotation status unchanged.

**4. The "Complete" button in Booking History was completely dead.** Two independent bugs stacked: (a) it called `PUT /api/bookings/:id`, which explicitly rejects any `status` field ("Use POST /api/bookings/:id/status..." — that route exists specifically so every status change is state-machine-validated and credits rewards) — so every click always failed; (b) it only rendered when `booking.status === "confirmed"`, but `completed` is never a valid transition from `confirmed` in `bookingStateMachine.ts` (it requires `trip_started`/`ongoing`/`extended`/`return_pending` first) — so even with bug (a) fixed, it could still never succeed from where it was shown. And with no `onError` handler, every failure was completely silent. Fixed both: switched to `POST /api/bookings/:id/status`, moved the button's visibility to the actual reachable-from-completed statuses, added error handling.

**5. Reward balance (and financial summary, bookings, payments) never refreshed after completing a booking.** `client/src/lib/queryClient.ts` sets `staleTime: Infinity` globally — a query never automatically refetches once cached, ever, for the life of the browser session, without an explicit `invalidateQueries` call. The one place that credits reward points (`POST /api/bookings/:id/status` transitioning to `completed`/`closed`) was only ever called from `live-bookings.tsx`, whose mutation invalidated just the live-ops list — never any customer-scoped query. A staff member with Customer 360 already viewed, then completing a trip, would see stale numbers until an actual hard page reload. Fixed in both `live-bookings.tsx` and the (now-corrected) `dashboard.tsx` Complete button: both invalidate the full customer query set (`/api/customers/:id`, `/rewards`, `/bookings`, `/payments`, `/financial-summary`, `/timeline`, and the list) whenever the response includes a `customerId`.

**Investigated, not reproduced:** a report of invoice totals coming out "2-3 rupees short" of the booking total. Tested exhaustively against the live server: whole-rupee amounts, fractional amounts (`6596.73`), toll/parking with `separate_non_taxable` treatment, and a discount — all four scenarios reconstructed to an exact `0.0000` discrepancy between `Booking.totalAmount` and `Invoice.totalAmount`. `finalizeInvoice()` doesn't recompute amounts at all (only assigns the invoice number and locks status), and the client-side `InvoiceDocument`/`invoice-template.tsx` just displays the stored value with no independent calculation. Genuinely unable to find or reproduce this one — needs exact repro numbers (the booking amount, the exact invoice total shown, document type, whether a discount/toll-split was involved) to investigate further.

New tests: `tests/e2e/lead-status-and-quotation-fallback.spec.ts` (3), `tests/e2e/quotation-whatsapp-pdf.spec.ts` (4), `tests/e2e/complete-booking-and-reward-refresh.spec.ts` (3, one environmentally skipped — see below) — all passing.

## Scope of Phase 10 — Availability Engine: buffers + cross-user tentative hold

A real, deliberately-scoped slice of the spec's "centralized zero-overlap Availability Engine with buffers/reservations" (§29-38) — not the whole thing. [docs/AVAILABILITY_RULE_MATRIX.md](./AVAILABILITY_RULE_MATRIX.md), written back in Phase 1, already recorded the exact gaps this closes.

**Buffers** — `findVehicleConflicts`/`findDriverConflicts` (`server/services/availability.ts`) gained an optional 7th parameter, `buffers?: { reportingBufferMinutes, returnBufferMinutes, restBufferMinutes }`, all defaulting to 0. Omitting it (every existing call site does) produces a query window byte-for-byte identical to before — verified by a dedicated regression test and by the full suite's pre-existing booking/driver-overlap tests all passing unchanged. Also added `checkVehicleAvailability`, a parity wrapper for the one documented gap where `checkDriverAvailability` existed but no vehicle equivalent did.

**Cross-user tentative hold** — the real, working part of "reservations." Rather than a new `ResourceReservation` model with its own create/expire/release lifecycle to keep in sync, this is a live read over the existing `BookingDraft` collection (Phase 8): a `BookingDraft` already *is* a per-user record of "I have this vehicle provisionally selected, for these dates, right now." New `findTentativeDraftConflicts()` queries other users' non-stale (< 20 minutes old — lazy expiry, no background job, matching this codebase's existing patterns) drafts for the same vehicle and overlapping dates. Wired into `storage-mongodb.ts`'s `createBooking()`, right after the existing real-booking conflict check: if another user currently has this exact vehicle selected for overlapping dates in their own open wizard, booking creation is rejected with `409 VEHICLE_TENTATIVELY_HELD` — a real, live-tested guard against two staff both completing a booking for the same vehicle at the same time, a gap the existing per-request `findVehicleConflicts` check (which only sees *real* Booking documents) could never catch. The current user's own draft is always excluded — finishing your own in-progress work is never blocked by itself.

Explicitly **not** built here (out of scope, unblocked-but-not-done or still blocked): filtering `GET /api/vehicles/available` by tentative holds (left untouched — the new guard is a last-mile create-time check, not an inventory-filtering overhaul); Vendor resource overlap (§33, still blocked — no Vendor Master on this branch); widening `Vehicle.status` for Service/Maintenance/Breakdown distinctions (§32, not needed by anything built so far).

## Two real, pre-existing bugs found and fixed during Phase 10 development

1. **`mongoBookingSchema` never declared a `createdBy` field**, so Zod's default object behavior (strip unrecognized keys) silently dropped it from every booking ever created through `POST /api/bookings` — `server/routes.ts` has correctly built `{userId, role}` into the payload since before this session, but it never survived `.parse()`. Found because the new self-exclusion check depends on knowing who is creating the current booking; confirmed via a direct API read that real, pre-existing bookings all had `createdBy: undefined`. Fixed by adding the field to the schema (one line, purely additive — cannot change behavior for any existing field). The Booking History "Created By" column, present in the UI this entire session, was very likely never actually populated until this fix.
2. **Deactivating a sub-user/manager does not free their slot** against the tenant's `maxManagers` create-time limit (`getManagersByTenant` counts by `role: 'manager'` only, not `isActive`) — found while writing this phase's cross-user test (needed a second real identity, hit "manager limit reached" after cleanup). Documented here as a real, separate, pre-existing gap; **not fixed** in this patch (out of scope for Availability Engine, deserves its own dedicated look at user-management capacity semantics). Worked around in the test file by reusing one fixture sub-user account across runs instead of creating a fresh one each time.

New tests: `tests/e2e/availability-engine.spec.ts` — 4 tests, all passing:
1. **API** — a normal booking creation with no `buffers` argument behaves exactly as before (also re-confirms the `createdBy` fix: the created booking's `createdBy.userId` is now real).
2. **API** — a user's own in-progress draft for the same vehicle+dates never blocks their own booking submission (self-exclusion).
3. **API** — using a real second identity (not a second browser tab on the same session), a second user's overlapping vehicle selection blocks booking creation with `409 VEHICLE_TENTATIVELY_HELD`; once the first user's draft is discarded, the exact same booking succeeds.
4. **API** — a non-overlapping date on the same held vehicle is never blocked.

All four retry with a fresh randomized date (and, for #1/#4, a randomly-picked available vehicle) if a given attempt happens to land on a genuine unrelated pre-existing `VEHICLE_DOUBLE_BOOKING` conflict — a real, demonstrated risk after this many hours of full-suite runs in this shared dev database (see regression notes below), not a flaw in the feature being tested. A `VEHICLE_TENTATIVELY_HELD` response is never retried past — that is the actual thing under test.

## Scope of Phase 8 — Booking wizard draft persistence

Closes the last piece of the original spec's "a smooth multi-step Booking Wizard with draft persistence and Previous/Next" ask — the Previous/Next stepping already existed (pre-existing `EnhancedBookingForm`, untouched); draft persistence did not. Adds one new model, `BookingDraft` — a single slot per `(tenantId, userId)`, not a list — auto-saved (debounced 1.2s) as the user fills in the existing wizard, so navigating away or refreshing mid-booking doesn't lose progress. Three new routes: `GET/PUT/DELETE /api/booking-drafts/mine`, scoped to `authenticateUser` + `requireTenant` only (a draft isn't a real booking yet, so it doesn't need its own permission key). On mount, `EnhancedBookingForm` checks for an existing draft and — if one is found — shows a "Resume your unfinished booking?" dialog (Resume / Start Fresh) rather than silently overwriting or silently resuming; the draft is deleted automatically the moment a real booking is actually created (in `createBookingMutation`'s `onSuccess`, not tied to any later confirmation-screen button click).

**Deliberately scoped OFF for a Lead-conversion prefill session** (`initialValues` present, from Phase 7): that flow already has its own source of truth (the Lead) and was built and verified as a self-contained path in the previous phase. The spec's actual ask — don't lose *organic* Add Booking progress — doesn't cover someone abandoning a Lead-conversion mid-way, and layering draft-resume on top would only add risk to an already-tested path for a case that isn't the one being asked for. Verified: a Lead-conversion session never shows the resume prompt and never reads or writes the draft slot, even when a real organic draft already exists in it.

New tests: `tests/e2e/booking-draft-persistence.spec.ts` — 5 tests, all passing:

2. **UI** — filling in Trip Details auto-saves a draft (confirmed server-side after the debounce window); navigating away and back to Add Booking shows "Resume your unfinished booking?"; clicking "Resume Booking" restores the exact fields.

## One real bug found and fixed during Phase 8 development (before it reached the test file)

**A race between the mount-time "does a draft already exist?" check and the same session's own debounced autosave.** The check fires an async `GET` on mount; if a fast typist (or, more realistically, a slow network on the initial `GET`) starts filling the form before that `GET` resolves, the 1.2s autosave can create a draft *first* — and the still-in-flight mount-time `GET` then sees that brand-new draft and shows "Resume your unfinished booking?" for what is actually the user's own current, uninterrupted progress. Caught live while smoke-testing with a script that fills all of Step 1 in rapid succession (mirroring a slow-network real-world case more than a normal human typing speed, but a real edge case regardless). Fixed with a `hasInteractedRef` guard: `form.formState.isDirty` becoming `true` is tracked via its own effect, and the mount-time check only shows the resume prompt if the user had *not* already started typing by the time it resolves.

## Scope of Phase 4 — Quotation system

## Real bugs caught and fixed during Phase 1 development (by these tests / by direct smoke-testing, not left in the code)

1. **Query-key mismatch prevented the Inquiries list from refreshing after creating a new inquiry.** The list page's `useQuery` used a single interpolated string (`` [`/api/inquiries?status=...&search=...`] ``) as its query key, while the create-mutation's `invalidateQueries({queryKey: ["/api/inquiries"]})` relies on TanStack Query's array-prefix matching. A single string element containing "/api/inquiries" as a substring does **not** prefix-match the plain `["/api/inquiries"]` key, so invalidation silently did nothing and the newly-created inquiry didn't appear until a manual reload. Caught via direct browser smoke-testing (screenshot showed "No inquiries found" immediately after a successful "Inquiry saved" toast), root-caused, and fixed by switching to the array-form key (`["/api/inquiries", statusFilter, search]`) already used by the existing `customers.tsx` page — bringing this new page in line with the established codebase convention rather than introducing a second pattern.
2. **Missing `RECEIPT_TYPES` import** in `server/routes.ts` (a leftover from the concurrent CEO Dashboard Phase 3 work in progress on this same branch before this task began) — caught immediately by `tsc --noEmit` before any further work, fixed by adding the import.
